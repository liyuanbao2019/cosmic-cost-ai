# 拆分校验规则

## 目标

只认可开发功能且具备明确数据移动的拆分结果。

当需求或拆分结果命中高风险表达时，应先核对原文证据。原文能够支持开发功能和数据移动时，才允许改写成可被专家认可的功能过程和 E/R/W/X；证据不足时必须标记为“待确认”，不得为了形成可计量结果而补写内容。

## 最高优先级硬约束

以下约束优先于本文其他拆分、改写和优化规则，任何情况下都不得违反：

1. 所有功能、数据移动、数据组和数据属性都必须能够定位到需求原文中的明确表述或明确含义，不得根据常见业务模式、经验模板或计量需要自行补写。
2. 原文证据不足、语义存在歧义或无法确认软件边界时，只能标记为“待确认”并说明缺少的证据，不得自动补充功能、E/R/W/X、数据组或数据属性。
3. 拆分优化以“忠实反映原始需求、专家复核后改动最少”为目标，不以增加 CFP、增加子过程数量、降低复用率或提高表面完整度为目标。

执行要求：

- 每个功能过程及其数据移动都应保留可追溯的原文依据。
- 改写只能澄清原文已经表达的业务事实，不能扩大、推断或创造需求范围。
- 当本文后续示例、映射或建议与上述硬约束冲突时，必须以上述硬约束为准。

## 1. 复用判定

相同或相似的以下内容出现两项及以上时，可判定为复用：

- 子过程描述
- 数据移动类型
- 数据组
- 数据属性
- 功能逻辑

## 2. 高风险表达与可计量改写

以下表达容易被判定为不具备独立数据移动：

- 匹配
- 解析
- 恢复
- 清除
- 计算
- 过滤
- 刷新
- 前台到后台
- 调研
- 设计
- 测试
- 上线
- 调优
- UI
- UE
- 规则校验
- 输入校验
- 合法性校验
- 支撑
- 集成
- 现场
- 实施

处理要求：

- 不要直接输出上述抽象词作为功能过程或子过程。
- 如果原需求有明确证据支持这些动作，应在不扩大原意的前提下改写成具备数据移动的开发功能。
- 改写时，只能根据原文明确谁输入了什么、系统读取了什么、系统写入或生成了什么、系统输出了什么；缺少的部分标记为“待确认”。

示例：

| 高风险表达 | 可计量改写方向 |
| --- | --- |
| 规则校验 | 用户提交校验条件；系统读取待校验数据；系统生成校验结果；系统返回校验明细 |
| 日志 | 用户提交日志查询条件；系统读取操作日志列表；系统返回日志详情 |
| 解析 | 用户上传待解析文件；系统读取文件内容；系统生成解析结果；系统返回解析明细 |
| 过滤 | 用户提交过滤条件；系统读取候选数据；系统返回过滤后的数据列表 |

## 3. 利旧风险表达

以下表达容易被判定为利旧：

- 接口
- 配置
- 页面设计
- 调用
- 日志
- 触发
- 提示

处理要求：

- 不要直接以“接口”“配置”“页面设计”“调用”“日志”“提示”作为功能过程。
- 如果确实属于开发功能，应改写成明确的输入、读取、写入、输出数据移动。
- 如果只是已有能力调用、页面样式调整或支撑性说明，应避免作为新增功能点输出。

## 4. 数据移动类型映射

| 关键词 | 数据移动类型 |
| --- | --- |
| 输入、导入、提交、上传、填报、录入、采集、接收、外部推送、拉取外部数据 | E |
| 校验、读取、查询 | R |
| 退出、展示、返回、输出 | X |
| 新增、删除、修改、编辑、写入、生成 | W |

## 5. 功能过程结构

一个功能过程必须满足：

- 子过程以 E 开头。
- 子过程以 W 或 X 结尾。
- 不允许连续 E。
- 至少包含两个子过程。
- 必须能形成明确的数据移动。

## 6. 数据属性

数据属性必须来自需求原文、表格字段、界面文字、接口定义或经人工确认的业务资料。

- 允许调整已有字段的排列和表达方式，但不得改变字段语义。
- 不得因为常见系统通常具有编号、状态、时间、操作人、结果说明等字段，就自动将这些字段补入数据属性。
- 原文只描述业务对象、未提供具体属性时，数据属性填写“待确认”，并提示人工补充证据。
- 枚举值、时间字段和标识字段只有在原文存在明确依据时才能写入。

## 7. 拆分策略

- 仅当原文能够证明存在独立触发事件、独立业务目的或独立业务结果时，才拆分为不同功能过程。
- 不得为了增加子过程数量、增加 CFP 或降低复用率而拆分功能、划分子模块或改写数据组。
- 模块层级应忠实反映需求原文的业务结构；单个功能点不应仅因计量需要升级为独立子模块。
- 查询、导出等相似功能只有在原文明确体现不同业务对象、数据组或输出结果时才能差异化；不得仅通过换词规避重复或复用判定。
