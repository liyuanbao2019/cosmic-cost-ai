# 拆分校验规则

## 目标

只认可开发功能且具备明确数据移动的拆分结果。

当需求或拆分结果命中高风险表达时，不应简单删除或判定为不计量，而应优先改写成可被专家认可的开发功能和 E/R/W/X 数据移动。

## 1. 复用判定

相同或相似的以下内容出现两项及以上时，可判定为复用：

- 子过程描述
- 数据移动类型
- 数据组
- 数据属性
- 功能逻辑

## 2. 高风险表达与可计量改写

以下表达容易被判定为不具备独立数据移动：

- 匹配
- 解析
- 恢复
- 清除
- 计算
- 过滤
- 刷新
- 前台到后台
- 调研
- 设计
- 测试
- 上线
- 调优
- UI
- UE
- 规则校验
- 输入校验
- 合法性校验
- 支撑
- 集成
- 现场
- 实施

处理要求：

- 不要直接输出上述抽象词作为功能过程或子过程。
- 如果原需求确实包含这些动作，必须改写成具备数据移动的开发功能。
- 改写时明确谁输入了什么、系统读取了什么、系统写入或生成了什么、系统输出了什么。

示例：

| 高风险表达 | 可计量改写方向 |
| --- | --- |
| 规则校验 | 用户提交校验条件；系统读取待校验数据；系统生成校验结果；系统返回校验明细 |
| 日志 | 用户提交日志查询条件；系统读取操作日志列表；系统返回日志详情 |
| 解析 | 用户上传待解析文件；系统读取文件内容；系统生成解析结果；系统返回解析明细 |
| 过滤 | 用户提交过滤条件；系统读取候选数据；系统返回过滤后的数据列表 |

## 3. 利旧风险表达

以下表达容易被判定为利旧：

- 接口
- 配置
- 页面设计
- 调用
- 日志
- 触发
- 提示

处理要求：

- 不要直接以“接口”“配置”“页面设计”“调用”“日志”“提示”作为功能过程。
- 如果确实属于开发功能，应改写成明确的输入、读取、写入、输出数据移动。
- 如果只是已有能力调用、页面样式调整或支撑性说明，应避免作为新增功能点输出。

## 4. 数据移动类型映射

| 关键词 | 数据移动类型 |
| --- | --- |
| 输入、导入、提交、上传、填报、录入、采集、接收、外部推送、拉取外部数据 | E |
| 校验、读取、查询 | R |
| 退出、展示、返回、输出 | X |
| 新增、删除、修改、编辑、写入、生成 | W |

## 5. 功能过程结构

一个功能过程必须满足：

- 子过程以 E 开头。
- 子过程以 W 或 X 结尾。
- 不允许连续 E。
- 至少包含两个子过程。
- 必须能形成明确的数据移动。

## 6. 数据属性

数据属性列可以通过以下方式增强可计量性：

- 更换字段顺序。
- 添加枚举值。
- 增加各类时间字段。
- 补充业务编号、状态、操作人、结果说明等可识别属性。

## 7. 拆分策略

- 尽可能把抽象表达改写为更多具备数据移动的子过程，但是一定是文档中具备的内容，不能凭空乱发散拆分。
- 通过划分多个子模块减少复用率。
- 对于单个功能点的新增，建议升级为子模块。
- 查询、导出容易被定义成重复，需要结合业务对象、数据组、输出结果进行差异化改写。
