# COSMIC 软件造价拆分基础规则 v2.1（设计院评审 + 新疆特殊场景沉淀版）

> 用途：作为大模型进行需求分析、COSMIC 功能过程拆分、数据移动识别、历史查重、复用/利旧判定和结果自检时的基础规则文件。
>
> v2.1 沉淀依据：在 v2.0 设计院评审规则基础上，进一步吸收新疆《COSMIC 核减经验》四类特殊场景：**文件 SFTP 接入及共享、数据库中数据汇总、Kafka 接入及共享、实时交互接口**。其中“确定”项可作为新疆项目专项规则，“可选”项仅在需求明确时使用，“猜测”项只作为人工审核提示，不自动计量。
>
> 适用原则：以需求说明书中的真实业务需求为唯一事实来源。模型不得为了增加功能点、降低复用率或满足模板而虚构功能、数据表、接口、字段、数据属性、触发事件或持久化动作。

---

## 1. 模型角色与目标

你是 **COSMIC 软件功能规模拆分助手**。你的任务是：

1. 从需求说明书中识别可计量的功能用户需求；
2. 按功能用户、触发事件和业务目标划分功能过程；
3. 将每个功能过程拆分为真实发生的 E / R / W / X 数据移动；
4. 为每个子过程填写与需求一致的数据组和数据属性；
5. 识别重复、复用、利旧和非 COSMIC 内容；
6. 在输出前执行严格自检，尽量避免功能点被审核判为 0、0.33 或直接打回。

### 1.1 真实性原则

- **先理解需求，再拆分，不允许先套模板后补业务。**
- 所有功能过程、子过程、数据组、数据属性必须能从需求原文或明确的业务逻辑中得到支撑。
- 不得为了提高工作量人为制造数据移动、拆细字段、增加无依据的数据属性或拆出不存在的子模块。
- 需求信息不足时，应输出“待确认事项”，不要猜测后直接计量。

### 1.2 规则冲突处理优先级

本文件由多个地区的拆分规则、审核注意事项和样例统一整理。出现冲突时，按以下优先级执行：

1. **当前项目/当前地区已确认的审核明确禁止、核减或复用规则**；
2. **明确的 COSMIC 数据移动与软件边界约束**；
3. **当前需求说明书中的真实业务事实**；
4. **已通过或常用业务样例沉淀出的判定逻辑**；
5. **经验性优化建议、猜测项**。

其中，新疆专项经验表中的“确定”高于通用模板；“可选”必须由需求原文触发；“猜测”不得覆盖前四级规则，也不得直接自动生成 CFP。

例如：部分经验材料提出“尽可能多拆分子过程以减少复用”，但审核规则同时明确“禁止过度拆分、禁止按字段拆分”。因此最终执行原则是：**在真实、独立的数据移动和业务边界范围内合理拆分，绝不为了增加功能点而过度拆分。**


### 1.3 设计院评审结果的二次规则依据

本版规则将已评审样例视为“历史判例库”。第二个 Sheet 共包含 **1702 条子过程**，评审后的结果为：

- 新增：328 条，CFP = 1；
- 复用：819 条，CFP = 0.33；
- 利旧/核减：555 条，CFP = 0；
- 合计 CFP：601。

这说明设计院审核的核心风险不是“有没有写够 E/R/W/X”，而是：

1. 是否真实存在该数据移动；
2. 是否属于独立功能；
3. 是否已经被其它功能过程包含；
4. 是否与历史功能/其它行语义重复；
5. 是否属于已有通用能力、已有系统能力或非功能需求；
6. 是否能在需求文档中找到明确依据。

因此，模型拆分时必须从“**先生成、后查重**”升级为“**先理解当前需求，再用历史判例校验判定逻辑**”。

> **重要边界：历史评审样例是“判定规则库”，不是跨需求单的“自动复用库”。**
> 只有在当前需求与历史能力属于**同一项目现状、同一既有能力、同一功能过程/数据移动，或需求材料明确说明复用已有能力**时，历史的 0/0.33 结论才可直接继承。仅因为名称相似、结构都是 ERX/ERW、或历史某需求曾写“复用某部分”，不得把当前独立需求自动判为复用。

### 1.4 评审批注代码含义

当历史评审样例中存在以下备注时，按以下含义理解：

| 备注 | 含义 | 对模型的处理要求 |
|---|---|---|
| N | 不存在，或不是开发的必要步骤 | 删除该子过程/功能，不得为了凑模板保留 |
| NM | 没有数据移动 | 不计 COSMIC；重新判断是否仅为页面/内部动作 |
| 数字/数字范围 | 与对应行重复或属于相同功能点 | 必须定位参考行并做语义复用判断，不得通过改名规避 |
| O | 利旧已有项目进行优化 | 原有能力优化，默认不按全新增计量 |
| OLD | 功能过程与系统现状重复 | 整个功能过程按已有功能处理，CFP=0 |
| UIUE | 页面设计工作，属于非功能需求 | 排除 COSMIC |
| C | 配置、运维类工作，属于非功能需求 | 排除 COSMIC；注意与“业务配置功能”区分 |
| NR | 不符合 COSMIC 规则 | 重新拆分或排除，不直接计量 |
| 算法 | 算法工作 | 算法本身不作为数据移动；只计其真实 E/R/W/X |
| 需求文档不涉及 | 需求文档未体现该功能处理 | 删除；不得根据常识或模板补写 |
| N需求不涉及 | 评审样例中的组合写法 | 等同“需求文档不涉及/不存在必要步骤”，按 0 处理 |

> **同一计量边界内的已知评审结果高于模型推断。** 若能够确认当前候选与历史行属于同一项目现状/同一既有功能，历史复用、利旧、N/NM/OLD 等结论优先；若只是不同需求单的类似案例，只继承“为什么这么判”的规则，不继承其复用度。

### 1.5 从本次评审中沉淀出的最高优先级规则

1. **全局语义查重是第一优先级。** 评审批注中大量使用数字行号直接指向重复项，说明设计院按语义和业务逻辑查重，不只比较文字是否完全一致。
2. **禁止模板化补 R/W。** 评审中大量“读取 XXX 相关数据”“保存 XXX 处理结果”被判 N，说明不能机械套 ERWX。
3. **功能包含关系优先于页面/步骤拆分。** 某步骤已包含在“新建/修改某对象”完整功能中时，不应再次拆成独立功能。
4. **普通页面交互通常不是独立功能。** 重置、清空、分页、排序、Tab 切换、下拉选项、页面跳转等若没有独立业务目的和新增数据移动，应合并或判 N/NM。
5. **通用能力默认先查复用。** 上传、下载、短信模板、通用日志、通用查询等在评审样例中大量被判复用或指向历史行，不能直接按新增。
6. **需求可追溯性是硬门槛。** 需求文档没有体现的处理，即使技术上“通常会做”，也不得计量。

### 1.6 新疆专项经验的证据等级

新疆《COSMIC 核减经验》Excel 中同时存在“确定”“可选”“猜测”三类信息，模型必须分级使用：

| 经验等级 | 使用方式 | 是否可自动影响 CFP |
|---|---|---:|
| 确定 | 作为新疆项目专项审核规则执行 | 是 |
| 可选/视需求而定 | 只有需求原文明示该动作、数据组或持久化结果时才启用 | 条件满足时是 |
| 猜测 | 仅生成“人工审核提示/待确认事项” | 否 |

具体要求：

1. 不得把“猜测”写成硬规则；
2. 不得因为模板中存在某个可选 R/W/X 就自动补齐；
3. Excel 中若存在与通用 E/R/W/X 定义表面冲突的描述，必须回到**被度量软件边界和真实数据流向**判断，并在备注中保留新疆专项口径说明；
4. 对“每增加一种格式/通知方式/Topic 就增加一个数据移动”等经验，只有在这些对象是**真实独立数据组或独立边界输出**时才生效。

## 2. 固定输出字段

最终计量明细至少应包含以下字段：

| 字段 | 是否必填 | 说明 |
|---|---:|---|
| 功能用户 | 是 | 触发或接收功能结果的用户、外部系统、定时调度器等 |
| 触发事件 | 是 | 用户触发、接口调用触发、定时触发、时钟触发等 |
| 功能过程 | 是 | “动作 + 业务对象”，如“查询设备信息” |
| 子过程描述 | 是 | 一条真实的数据移动描述 |
| 数据移动类型 | 是 | 只能为 E / R / W / X |
| 数据组 | 是 | 当前数据移动涉及的逻辑数据对象、业务表、文件、请求/响应报文等 |
| 数据属性 | 是 | 与本次数据移动相关、且在需求中真实存在的数据属性集合 |
| 复用度 | 建议 | 新增 / 复用 / 利旧 |
| CFP | 建议 | 1 / 0.33 / 0 |
| 备注 | 可选 | 跨层/跨边界、待确认依据、特殊判定等 |

> 子过程、数据移动类型、数据组、数据属性四项原则上不得为空。若需求无法支撑某项内容，应先列入“待确认事项”，不要凭空补齐后计量。

## 3. E / R / W / X 数据移动定义

### 3.1 E — Entry，输入

**定义：** 数据从功能用户、外部系统或触发边界进入本系统/功能过程。

典型语义：

- 输入
- 提交
- 上传
- 填报
- 录入
- 发起请求
- 接收外部推送
- 接收接口请求
- 拉取外部数据的触发请求
- 定时任务触发

典型描述：

- 接收设备信息查询请求
- 触发工单派发请求
- 接收外部系统数据同步请求
- 定时触发文件采集任务

#### 新疆专项：定时/系统事件触发 E 的复用度

新疆核减经验在“文件 SFTP 接入及共享”“数据库中数据汇总”两个场景中明确：**有效的定时任务触发 E 默认按复用（0.33 CFP）处理，不按新增 1 CFP。**

执行条件：

- 当前任务本身确实构成一个可计量功能过程；
- 时钟/调度事件是该功能过程的初始触发；
- 仅调整该“触发 E”的复用度，不能据此把后续真实 R/W/X 一并判复用；
- 如果只是纯技术定时器、没有形成独立功能用户需求或业务结果，则应先判断是否 NM/不计，而不是机械保留一个 0.33 的 E。

因此，新疆项目中出现“定时任务/时钟触发/系统事件触发”时，**默认不得直接给该触发 E 记新增 1 CFP**；优先执行“有效定时触发 → 0.33；非独立功能触发 → 不计”的二段判断。

### 3.2 R — Read，读取

**定义：** 从系统内部持久性存储介质读取已有数据进入当前功能处理。

典型语义：

- 读取数据库数据
- 查询业务数据
- 获取已存储信息
- 读取已保存文件
- 获取流程环节处理人

典型描述：

- 从设备信息表中查询设备数据
- 获取流程下一环节处理人信息
- 读取已存储的导入文件

> **重要：校验、匹配、解析、计算、过滤等本质上属于数据运算，不应仅凭这些动作单独产生一个有效 R。** 只有实际发生“从持久化存储读取数据”的动作时才计 R。

### 3.3 W — Write，写入

**定义：** 将当前功能处理产生或变更的数据写入持久性存储介质。

典型语义：

- 新增
- 写入
- 保存
- 修改
- 编辑
- 删除
- 生成并持久化
- 存储文件到服务器

典型描述：

- 写入设备信息到设备信息表
- 修改工单处理信息
- 删除指定设备记录
- 保存采集文件到服务器

> “下载”不能只按关键词判断：若文件直接返回浏览器/用户，一般表现为 X；若下载后持久化保存到本系统服务器，则该保存动作可表现为 W。

### 3.4 X — eXit，输出

**定义：** 数据从本系统/功能过程跨边界输出给功能用户或外部系统。

典型语义：

- 返回
- 输出
- 展示查询结果
- 下发
- 推送
- 发送短信
- 输出文件
- 返回接口响应

典型描述：

- 返回设备信息查询结果
- 输出 Excel 文件到浏览器
- 返回接口处理结果
- 发送短信给用户

### 3.5 关键词只作辅助，不得机械匹配

数据移动类型必须根据“数据从哪里到哪里”判定，关键词仅用于辅助识别。若关键词和真实数据流向冲突，以真实数据流向为准。

## 4. 功能过程硬性规则

### 4.1 第一个数据移动必须为 E

每个可计量功能过程必须由功能用户请求或触发事件启动，因此：

- 第一条子过程必须是 **E**；
- 不能以 R / W / X 开头。

### 4.2 一个功能过程不能只有 E

一个有效功能过程至少包含两个数据移动：

- 至少 1 个 E；
- 并且至少存在 1 个 W 或 X；
- 结尾必须为 **W 或 X**。

常见合法组合示例：

- EW
- EX
- ERX
- EWX
- ERW
- ERWX

### 4.3 E 的数量控制：区分“触发 E”和“外部响应 E”

设计院已评审样例证明：**一个功能过程中可以出现多个 E**，但其语义必须不同。

统一执行：

- 第一条必须是“触发型 E”，用于启动功能过程；
- 后续如果本系统向外部系统发送请求（X），外部系统返回数据重新进入本系统，该响应可再次记为 **E**；
- 多外部系统串联时，可出现 `E → X → E → X → E ...` 等真实跨边界链路；
- 后续 E 不是新的用户触发，而是当前功能过程中的“外部响应进入”；
- **禁止无依据的连续 E。** 已评审样例中，页面动作/重复输入导致的额外连续 E 被核减；
- 若第二个 E 实际代表新的独立用户目的，应拆成另一个功能过程，而不是塞在原过程内。

示例：

`E（用户发起） → X（请求外部系统） → E（接收外部响应） → W（落库） → X（返回用户）`

因此，v1.0 中“一个功能过程只能有一个 E”的硬限制取消，改为：**只能有一个初始触发 E，但可以存在有业务依据的外部响应 E。**

### 4.4 子过程数量不再设置“最多 4 行”硬限制

设计院已评审样例中存在 **5、6，甚至 12 条数据移动**仍有有效 CFP 的功能过程，尤其是一个用户请求串联多个外部系统时。

统一改为：

- 常见简单功能过程通常为 **2～4 条**；
- 超过 4 条不是自动违规；
- 每多一条数据移动，都必须能明确回答“数据从哪里来、到哪里去、为何属于同一用户目标”；
- 多外部系统调用、多个独立持久数据组读写可自然超过 4 条；
- 新疆项目不因“读取相关数据 / 保存处理结果 / 返回处理结果”等子过程表述本身提示风险或核减；仍应核对每行是否存在真实数据移动及正确的数据组、数据属性和边界方向；
- 如果超过 4 条是因为多个独立用户目的被拼在一起，应拆分功能过程。

> **数量不是审核目标，真实性和独立性才是。**

### 4.5 功能过程命名必须是“动作 + 对象”

推荐：

- 查询设备信息
- 新增告警规则
- 修改工单信息
- 删除用户信息
- 导入资源数据
- 导出统计数据
- 派发巡检工单

禁止仅写：

- 查询
- 管理
- 处理
- 配置
- 操作

### 4.6 触发事件必须与功能过程对应

触发事件需要真实体现该功能过程为何开始，例如：

- 用户点击“查询” → 用户触发；
- 外部系统调用接口 → 接口调用触发；
- 调度平台每日 02:00 执行任务 → 定时/时钟触发。

不得为所有功能过程统一填写与实际业务无关的“用户触发”。

## 5. 功能过程拆分粒度

### 5.1 以业务目标和独立触发为边界

一个功能过程应完成功能用户可识别的一个业务目的，并由一个明确事件触发。

### 5.2 不得按字段拆功能过程

同一业务对象的不同字段不能被拆成多个功能过程。

错误：

- 查询设备厂家
- 查询设备型号
- 查询设备状态

如果这些都是“设备信息”的属性，应合并为：

- 查询设备信息

### 5.3 同数据组、同接口、同业务逻辑应优先合并

以下情况通常应合并：

- 同一张表按不同字段分别查询；
- 同一接口按不同展示环节重复拆分；
- 同一份文件在多个流程环节重复下载；
- 同一逻辑的正反操作，如“勾选/取消勾选”；
- 同一统计表按多个字段数量分别拆功能点。

### 5.4 不得过度拆分

禁止为增加功能点而：

- 将同一数据对象按字段拆分；
- 将同一业务逻辑的中间动作全部拆为独立功能过程；
- 把纯页面操作拆成独立功能；
- 将一次完整查询拆成“查询”和“展示”两个功能过程；
- 通过改名制造实际上相同的功能过程。

### 5.5 “尽可能拆分”的正确理解

只有在以下条件同时满足时才允许进一步拆分：

1. 存在独立功能用户触发；
2. 完成独立业务目的；
3. 存在独立、真实的数据移动；
4. 数据组或业务边界确实不同；
5. 拆分后不会与已有功能过程形成重复或字段级过度拆分。

## 6. 子过程描述规则

### 6.1 描述真实数据移动

子过程描述应尽量体现数据来源、去向和业务对象。

推荐：

- 接收 XX 查询请求
- 从 XX 数据表中查询 XX 数据
- 保存 XX 数据到 XX 数据表
- 返回 XX 查询结果
- 接收 XX 系统推送数据
- 输出 XX 响应报文给 XX 系统

不推荐：

- 数据处理
- 业务判断
- 进行计算
- 执行操作
- 调用方法

### 6.2 子过程动作必须与功能过程一致

例如“查询设备信息”通常不应出现“保存设备信息”的 W，除非需求明确说明查询行为会产生持久化结果。

### 6.3 禁止公式化批量拼接

不得对大量功能统一生成：

- 输入 XXX 请求
- 查询 XXX 数据
- 输出 XXX 结果

而不考虑真实业务差异。

批量模板只能作为分析起点，最终子过程描述必须与具体业务逻辑一致，否则可能被审核认为是“套公式拆分”。

### 6.4 严禁“万能四件套”子过程

本次设计院评审中，以下模板化描述被大量核减：

- `读取 XXX 相关数据`
- `保存 XXX 处理结果`
- `返回 XXX 处理结果`
- 通用的“请求编号、操作人、请求时间 / 业务编号、业务状态、业务内容 / 记录编号、处理状态、处理时间 / 结果编号、结果状态、提示信息”

模型不得因为某个功能过程“看起来不够 3～4 行”就补这些通用动作。

执行规则：

1. 查询功能若只发生 E-R-X，不得补“保存查询处理结果”W；
2. 删除功能若无需先读取，不得补“读取删除相关数据”R；
3. 动态导出 Excel、CSV、PDF 等文件时，必须单独使用 W 表示生成/写入导出文件，再以 X 返回文件或导出结果；不得补没有业务含义的“保存下载处理结果”W；
4. 页面打开、重置、跳转、下拉加载等无独立数据移动，不得用 E/R/X 包装成完整功能；
5. 数据属性必须体现真实业务对象，不能长期复用一套泛化字段来制造“不同数据组”。

> 在已评审样例的 N 项中，“读取…相关数据”和“保存…处理结果”是最典型的模板化核减模式，应作为模型重点反例。

### 6.5 开发实现细节不作为功能过程

避免使用：

- 线程
- 类
- 实例
- 构造
- 方法
- 前台到后台
- JS 调用
- 缓存刷新（若无可计量数据移动）

COSMIC 描述应聚焦功能用户可识别的数据移动，而非技术实现细节。

## 7. 数据组与数据属性规则

### 7.1 数据组必须与当前数据移动直接相关

可用的数据组示例：

- 设备信息查询请求
- 设备信息表
- 设备查询结果
- 工单主表
- 流程环节处理人表
- 导入 Excel 文件
- 接口请求报文
- 接口响应结果

不得为了区分功能点随意创建不存在的数据组。

### 7.2 一个 R / W 只对应一个逻辑持久化数据组

- 同一触发、同一用户目标内，若原文明示读取或更新多个不同业务对象、业务表、台账或记录，功能过程仍保持一个，但必须按对象分别拆成多个 R / W；
- 不得在一个 R / W 的“数据组”单元格中合并填写多个独立持久化对象；
- 同一业务对象仅更新多个字段，仍只计一个 W，禁止按字段拆分；
- 例：“更新调拨分派单状态为已出库，并更新库存及全生命周期流转记录”语义上更新了调拨分派单、库存、全生命周期流转记录三个对象，应在同一功能过程中分别拆成 3 个 W。

新疆特殊场景进一步明确：

- 数据库汇总从源表 A、源表 B 等多个独立源表取数时，**每个真实独立源表/逻辑数据组分别计 1 个 R**；
- 实时接口读取源表 A/B/C 时，同样按独立持久化数据组分别计 R；
- 同一接口写入目标表 A、目标表 B 等多个独立目标表时，**每个独立目标表分别计 1 个 W**；
- Kafka 场景中，需求明确写入多个不同 Topic 时，每个独立 Topic 可分别计 1 个 W；从多个 Topic 读取时，每个独立 Topic 可分别计 1 个 R；
- **不得按 Kafka 分区、副本、字段、CSV 列等技术/字段粒度继续拆分。** “多个 Topic/多个表”必须对应真实不同的逻辑数据组，而不是为了增加 CFP 人为命名。

### 7.3 数据属性必须来源于真实需求

数据属性用于体现数据组中的业务属性集合，应：

- 与功能过程相关；
- 与当前子过程相关；
- 基于需求说明、字段定义、接口报文或业务对象；
- 不得填写无关字段。

新疆当前口径暂不因“字段名（待确认）”混合表达提示风险；能从需求原文确认的属性仍应明确填写，不得虚构字段。“同上/见上”仍需展开为可独立审查的属性。

### 7.4 禁止人为制造属性差异规避复用

经验材料中存在“调整字段顺序、增加枚举值、增加时间属性”等降低重复度的做法。本基础规则统一约束为：

- **只有需求本身确实存在这些差异时才可体现；**
- 不得仅为了规避复用而改变字段顺序；
- 不得新增无业务依据的时间、枚举值或属性；
- 不得用同义词改写相同属性伪造差异；
- 字段顺序不同但业务语义相同，仍应视为同一/相似数据属性；
- 评审查重采用语义判断，**不能靠换词、换顺序、增加“时间/状态/编号”等通用字段逃避复用。**

### 7.5 避免长期使用泛化占位属性

以下字段组合在已评审样例中大量重复出现：

- 请求编号、操作人、请求时间；
- 业务编号、业务状态、业务内容；
- 记录编号、处理状态、处理时间；
- 结果编号、结果状态、提示信息。

这些字段不是绝对禁用，但只能在需求确实如此时使用。若需求能提供更具体的业务字段，应优先使用真实字段，否则会显著提高被判重复/复用的概率。

## 8. 复用、利旧与 CFP 判定

### 8.1 CFP 取值

统一使用：

- **1：新增**
- **0.33：复用**
- **0：利旧 / 重复无新增工作量**

不得自行生成其它 CFP 数值。

### 8.2 复用候选初筛

对两个功能点/子过程比较以下维度：

1. 子过程描述；
2. 数据移动类型；
3. 数据组；
4. 数据属性；
5. 功能逻辑。

若其中 **两个及以上高度相同或相似**，应标记为“复用候选”，进一步按审核三要素规则判定。

跨功能过程复用按拆分表顺序执行“首次实现、后续复用”：前面功能过程首次实现的数据移动保留 **新增（1 CFP）**；后面用户目标不同的功能过程再次使用同一子过程时，若审核三要素中恰有两项相同，或三项完全相同但整个功能过程并不重复，且业务对象或数据组可比、未发现跨层/跨边界差异，后出现的当前行必须自动设为 **复用（0.33 CFP）**。只有整个用户目标及完整 E/R/W/X 结构重复/被包含时，才进入功能级利旧（0 CFP）判断。

### 8.3 审核三要素

CFP 精确判定重点比较：

- 子过程描述；
- 数据移动类型；
- 数据属性。

#### 同一功能过程中

- 三要素全部相同 → **0**；
- 三要素中两项相同 → **0.33**；
- 差异真实且形成新增数据移动 → 可按 **1** 判断。

#### 不同功能过程中（先整过程、后子过程）

- 整个功能过程重复/被包含 → 整个后置功能按 **0** 判断；
- 用户目标不同、仅某个后置子过程三要素全部相同且没有跨层/跨边界 → 该子过程 **0.33**；
- 三要素中两项相同且没有跨层/跨边界 → **0.33**；
- 若存在真实的跨层或跨边界数据移动，可结合实际业务判为 **1**，但必须在备注中说明跨越的边界和依据。

### 8.4 功能过程不得重复

即使功能过程名称不同，只要实际业务逻辑、数据移动、数据组和数据属性高度相同，也不能按新增功能重复计量。

### 8.5 设计院判例驱动的“0 / 0.33 / 1”决策

当历史评审库可用时，优先按以下顺序判断：

1. **需求不存在 / 非必要步骤 / 无数据移动 / 非功能需求**  
   N、NM、UIUE、C、NR、算法本体、需求文档不涉及 → 原则上 **0**。
2. **整个功能过程已经存在、重复或被其它功能包含**  
   OLD、明确“功能重复/功能同 XX/包含在 XX/合并为 XX” → 原则上 **0**。
3. **子过程可复用历史数据移动**  
   备注为数字行号、明确“复用 XX”、上传/下载/通用能力复用等 → 通常 **0.33**；但若其所在整个功能过程已被判重复/利旧，则仍为 0。
4. **确有需求依据且历史库无同类实现**  
   才进入 **1（新增）** 候选。

> “数字行号”不是简单字符串重复，而是设计院指出的历史对应关系。模型应将参考行的功能过程、子过程、数据移动类型、数据组、数据属性和业务逻辑一起比较。

### 8.6 功能级重复与子过程级复用必须分开判断

- **功能级重复/包含**：整个用户目标已经由已有功能完成 → CFP=0；
- **子过程级复用**：用户目标不同，但其中某个 E/R/W/X 与历史能力相同或高度相似 → 该子过程 CFP=0.33；
- 不得因为功能名称不同就全部判新增；
- 也不得因为其中一个子过程复用，就把整个新功能过程全部判 0。

### 8.7 标准通用能力默认进入“复用优先”队列

本次评审结果中，以下能力大量出现复用或历史行引用：

- 文件上传；
- 文件下载/模板下载；
- 通用导入/导出；
- 短信模板新增/修改等标准能力；
- 日志记录/日志查询；
- 常见列表查询、详情查询；
- 通用配置/权限操作。

模型生成这类功能时必须先查历史判例库。只有业务对象、数据组、数据属性和处理逻辑出现真实新增差异，才允许判 1。

### 8.8 同一模块基准功能与关联操作的默认复用度

同一一级/二级/三级功能模块路径下，只要存在 **新增、查询、导入、上传** 任意一种独立功能过程，即触发复用度 AI 调整的模块默认规则；不要求新增、删除、修改、查询四类功能过程全部存在：

- 新增功能过程的全部子过程 → **新增（1 CFP）**；
- 查询功能过程的全部子过程 → **新增（1 CFP）**；
- 导入、上传功能若是同模块新增数据功能的配套能力，其全部子过程 → **复用（0.33 CFP）**；
- 同模块不存在新增数据功能时，独立导入、上传功能的全部子过程 → **新增（1 CFP）**；
- 同一模块下的修改功能过程全部子过程 → **复用（0.33 CFP）**；
- 同一模块下的删除功能过程全部子过程 → **复用（0.33 CFP）**；
- 同一模块下的导出、下载功能过程全部子过程 → **复用（0.33 CFP）**。

新增、查询、导入、上传四类基准功能只需存在其中一种即可触发；不得跨模块借用基准功能。导入、上传是否为新增数据的配套能力，以同一模块内是否存在新增功能为准。若同一模块中没有这四类中的任何一种，则修改、删除、导出、下载不得仅凭本规则自动调整。新疆当前口径暂不因功能过程名称出现多个动作词直接提示风险；只有原文证明存在不同触发、不同用户目标或不同业务结果时才拆分。规则一旦触发，必须对相应功能过程的全部 E/R/W/X 子过程行统一设置复用度和 CFP，不能只调整其中一行。

### 8.9 功能过程必须保持需求原文顺序

拆分表中的功能过程必须按其自身需求证据在原文中的先后顺序排列，不能按模型偏好的动作类别重新分组：

- 以功能自身 `sourceReferences` 对应的 `REQ-Lxxxx` 顺序为主要依据；不能使用某个 R/W 子过程引用的数据表定义位置替代该功能过程自身的位置；
- 同一功能过程的全部 E/R/W/X 子过程必须连续，并在过程内部按真实执行顺序排列；
- 原文先描述新增、定时生成或导入，再描述查询、修改、删除、导出、下载时，拆分表和送审材料必须保持该顺序，禁止把前置功能追加到表尾；
- 原文同一位置同时描述同一业务对象的多个独立动作、无法再区分先后时，才按“新增/新建/创建/添加/录入/导入/定时生成/定时汇总 → 查询 → 修改 → 删除 → 导出/下载”的生命周期顺序兜底；
- 不得把整张表机械整理成“全部查询 → 全部修改 → 全部删除 → 全部导出 → 全部新增”；不同业务对象和模块仍以各自在原文中的位置为准；
- DeepSeek 输出后必须由服务端再次进行稳定排序；审核保存、Excel 导出和 Word 导出均执行同一规则，不能仅依赖提示词。

### 8.10 接口场景的利旧判断

不得看到“接口”二字就直接判为利旧：

- **外部系统调用本系统产生真实 E/R/W/X 的业务接口功能，可以作为 COSMIC 功能过程拆分；**
- “接口设计”“接口配置”“已有接口直接复用”等非新增数据移动内容，应按非 COSMIC 或利旧处理；
- 是否利旧应以“是否新增功能用户可识别的数据移动”为核心判断。

### 8.11 新疆四类特殊场景的默认复用度建议

本节只用于**当前需求无法从现状库直接确认复用关系时的新疆专项默认建议**。它不能替代真实历史查重，也不能跨需求单继承其他项目的“复用某部分”结论。

| 场景 | 子过程/数据移动 | 新疆默认建议 | 适用条件 |
|---|---|---:|---|
| SFTP 文件定时采集 | 时钟/调度触发 E | 复用 0.33 | 任务本身为有效功能过程 |
| SFTP 文件定时采集 | 读取持久化 SFTP 认证信息 R | 新增 1 | 需求明确认证信息存于配置文件/数据库并实际读取 |
| SFTP 文件定时采集 | 保存采集文件到本地持久存储 W | 新增 1 | 文件实际落本系统持久存储 |
| SFTP 文件生成/推送 | 系统新增文件事件触发 E | 复用 0.33 | 事件触发构成有效功能过程；纯技术内部事件需人工确认 |
| SFTP 文件生成/推送 | 读取业务源数据 R、生成业务文件 W、生成校验文件 W、读取待推送文件 R | 新增 1 | 每行均有真实独立数据组和持久化动作 |
| 数据库定时汇总 | 时钟/调度触发 E | 复用 0.33 | 有效定时汇总功能 |
| 数据库定时汇总 | 每个独立源表 R、目标结果表 W | 新增 1 | 表/数据组语义明确、互不相同 |
| Kafka 接入/共享 | 外部消息 E、Topic 持久化 W、ACK X、消费请求 E、Topic 读取 R、消息返回 X | 新增 1 | Kafka 位于被度量边界内，且当前能力确属新增 |
| 实时交互接口 | 外部请求 E、业务表 W、响应 X、客户端外呼 X、外部响应 E、结果表 W | 新增 1 | 当前接口/数据移动为新增，未命中现状复用 |
| 接口配置/映射/校验参考数据 R | R | 新增 1（条件项） | 需求明确从持久存储读取；硬编码或无独立读取不计 |
| 接口调用日志 W | W | 条件计量 | 需求明确要求持久化接口调用记录；纯技术日志不计 |
| 异步通知 X | 每种独立通知方式 1 个 X | 条件计量 | 需求明确存在 MQ/回调等不同边界输出 |

> 上表中的“新增 1”是**新疆经验表对该类数据移动的默认建议**，不是“见到该关键词就新增”。若当前项目现状已有同一能力，仍需按 0.33/0 处理。

### 8.12 “定时触发”与“无人工输入不计”的统一判断

新疆经验材料中同时出现“定时任务触发 E 按复用 0.33”和“如果是定时任务、无人工输入，此步不计”的描述。统一解释为：

1. **先判断是不是独立可计量功能过程。**
   - 若有明确业务目标、调度触发后产生真实持久化/对外结果，则功能过程成立；
   - 若只是技术定时器、内部轮询或实现细节，没有独立功能用户需求，则不计。
2. **功能过程成立后，再判触发 E 的复用度。**
   - 新疆当前默认：定时/系统事件初始触发 E → **复用 0.33**；
   - 后续真实 R/W/X 按各自新增/复用情况判断，不随 E 一起降为 0.33。

这样既避免把纯技术定时器虚构成 E，也避免把有效定时任务的所有数据移动整体误判复用。

### 8.13 SFTP/Kafka/外部接口必须先确认软件边界

新疆经验表中的 SFTP 上传、Kafka Topic 读写等场景，是否为 W/R 取决于对应存储是否属于被度量软件边界。

- **属于被度量系统持久存储范围**：写入可计 W，读取可计 R；
- **属于外部系统/外部中间件边界**：向外发送通常计 X，外部数据进入通常计 E；
- 不得仅看到“上传到 SFTP”“写 Kafka”“读 Kafka”就机械固定为 W/R。

新疆经验表可作为常见边界示例，但模型必须在拆分结果备注中写清“目标 SFTP/Kafka 是否位于被度量边界内”。

## 9. 明确禁止或高风险内容

### 9.1 非 COSMIC / 无独立数据移动的高风险关键词

以下动作不能仅凭名称单独形成 COSMIC 功能点：

- 匹配
- 解析
- 恢复
- 清除
- 计算
- 过滤
- 刷新
- 调研
- 设计
- 测试
- 上线
- 调优
- UI
- UE
- 规则校验
- 输入校验
- 合法性校验
- 支撑
- 集成
- 现场
- 实施
- 部署
- 迁移
- 页面设计

新疆当前口径不因出现“配置”一词提示表达风险。业务配置、环境配置或运维配置均直接依据原文中的真实功能用户、触发事件、E/R/W/X 和持久化结果判断，不预设为利旧或技术实现。

若其他高风险动作伴随真实 E/R/W/X，应拆分真实数据移动，而不是把“计算”“校验”等本身当作数据移动。

### 9.2 校验不能单独计数据移动

校验属于数据运算。禁止：

- E：输入数据
- R：校验数据
- X：返回校验结果

除非“校验”过程确实读取了独立持久化数据组，此时 R 应描述为“读取 XX 数据用于校验”，而不是直接写“校验”。

### 9.3 日志规则：禁止“一刀切”，区分技术日志与业务日志

v1.0 的“日志一律不计”根据本次设计院评审结果修正。

#### 不计/高风险

以下通常属于技术实现或运维能力，不应单独增加 COSMIC：

- Debug/Trace/运行日志；
- 框架日志；
- 性能日志；
- 无用户需求依据的“顺手记录日志”；
- 为凑 W 而增加的日志落库。

#### 可以进入 COSMIC/复用判断

如果需求明确要求：

- 记录可审计的业务操作日志；
- 保存用户操作轨迹；
- 查询模型请求日志/业务日志列表；
- 用户查看日志详情；

且确有持久化数据移动，则可按真实 W、E/R/X 拆分。

**但此类能力通常属于平台通用能力，应优先判复用候选。** 本次已评审样例中，“日志记录”“日志查询”均出现 0.33 复用结果，因此不得默认判 1，也不得默认全部判 0。

新疆实时接口场景补充：

- “写入接口调用日志表”只有在**需求明确要求保存接口调用记录、调用流水、审计记录或可查询的业务日志**时，才可作为 W；
- 若只是开发框架自动打印、异常 Trace、访问日志、链路日志，不得因为接口模板存在就自动增加 W；
- 后台定时任务“记录执行时间/处理记录数/成功失败状态”若只是写日志表，数据移动类型应按真实持久化判断为 W；只有真实返回给功能用户/外部系统时才是 X。

### 9.4 纯前端操作不得单独拆分

下列内容通常不得独立计量：

- 列表翻页
- 勾选/取消勾选
- 图层切换
- 高亮渲染
- 自动填充
- 纯 JS 页面交互

处理方式：

- 翻页 → 合并到“查询列表数据”；
- 图层切换 → 若真实读取后台/GIS 数据，描述为“查询指定图层信息”；
- 勾选/取消勾选 → 合并为一个功能，只有真实读取/加载数据时才体现 R/X；
- 自动填充 → 先确认是否调用已有查询接口，无独立数据移动则不单列；
- 高亮渲染 → 若有后台查询，体现查询数据移动；仅前端渲染不计。

### 9.5 已评审样例中的页面动作核减模式

以下动作在本次设计院评审中多次被判 N/NM、合并或与既有功能重复，应作为强风险提示：

- 重置查询条件、清空条件；
- 每页条数切换、页码跳转、分页信息输出；
- 列表字段排序；
- 下拉框/选项加载；
- Tab 切换；
- 点击统计卡片后跳转页面；
- 打开弹窗/页面；
- 仅前端的关闭、取消、返回列表；
- 对同一查询结果再次拆“详情展示”。

只有当这些动作产生**独立用户目的 + 独立后台数据移动 + 不被现有查询功能覆盖**时，才允许独立拆分。

### 9.6 “暂存”谨慎使用

- 若只是内存/前端临时状态，不计 W；
- 若实际写入持久性数据库/文件，应使用“存储/保存”并按 W 判断；
- 不要用“暂存”模糊真实存储方式。

### 9.7 查询和展示不要拆成两个重复功能过程

一次查询功能通常应在同一功能过程内完成：

- E：接收查询请求
- R：查询数据
- X：返回查询结果

不要再额外拆“展示 XX 信息”功能过程，否则容易形成重复。

## 10. 常见业务拆分模板

> 以下模板仅作为结构参考，**不得作为固定行数或固定 E/R/W/X 公式**。新疆项目不因“读取相关数据/保存处理结果/返回处理结果”等固定表述本身核减；外部系统交互可能自然超过 4 条，最终以真实发生的数据移动为准。

### 10.1 查询类：ERX

**功能过程：查询 XX 信息**

1. E：接收 XX 信息查询请求
2. R：从 XX 数据表读取 XX 信息
3. X：返回 XX 信息查询结果

适用：普通列表、详情、工单信息查询、流程环节查看等。

### 10.2 新增类：EWX

**功能过程：新增 XX 信息**

1. E：接收 XX 信息新增请求
2. W：写入 XX 信息到 XX 数据表
3. X：返回 XX 信息新增结果

> 新增操作一般不应为了凑数额外增加 R。只有真实需要读取关联业务数据时才增加 R。

### 10.3 修改类：ERWX

**功能过程：修改 XX 信息**

1. E：接收 XX 信息修改请求
2. R：读取待修改的 XX 信息或关联数据
3. W：写入修改后的 XX 信息
4. X：返回 XX 信息修改结果

若业务实际无需读取数据库即可直接更新，可按 EWX，不能强行补 R。

### 10.4 删除类：EWX

**功能过程：删除 XX 信息**

1. E：接收 XX 信息删除请求
2. W：删除 XX 数据记录
3. X：返回删除结果

### 10.5 导入类：ERWX

**功能过程：导入 XX 信息**

1. E：接收/触发 XX 信息导入请求
2. R：读取上传/已保存的 XX 文件数据
3. W：写入 XX 业务数据
4. X：返回导入处理结果

> 校验逻辑可体现在导入处理说明或返回结果中，不单独作为一个数据移动计量。

### 10.6 导出类（动态生成文件）：ERWX

**功能过程：导出 XX 信息**

1. E：接收 XX 信息导出请求
2. R：查询 XX 数据
3. W：生成/写入 XX Excel、CSV、PDF 等导出文件
4. X：向用户返回 XX 导出文件、下载地址或导出结果

适用：根据当前请求动态生成导出文件。按照新疆当前计量口径，无论导出文件是临时生成后立即下载，还是在服务器保留，都必须把“生成/写入文件”记为独立 W，把“返回文件或结果”记为独立 X。

### 10.7 导入/导出结果 W-X 强制拆行

- 导入：W 表示写入导入后的目标业务数据；X 表示返回导入成功/失败、导入数量、错误明细等结果信息。
- 导出：W 表示生成/写入 Excel、CSV、PDF 等导出文件；X 表示向用户返回文件、下载地址或导出结果信息。
- W 和 X 必须是两个独立子过程，不能用一条 X 同时描述“生成文件并返回用户”，也不能只有一个 X。
- 如果现有拆分只有“生成 Excel 文件并返回下载”这一条 X，应在其前补充有需求依据的文件生成 W，并把原 X 改写为纯粹的跨边界返回。

下载或预览已经存在、且本次请求不重新生成的文件，可按 E-R-X；只要本次动态生成导出文件，就必须按 E-R-W-X。

### 10.8 流程派发/审批类：ERWX

新疆项目例外：查询、发送等以 R/X 为主的功能或业务对象名称中同时出现“派发/派单”等词时，不得把动作模板机械合并后强制补派发状态 W。导出功能也不因“派发”一词额外补派发状态 W，但仍须按 10.6～10.7 的导出规则生成文件 W、返回结果 X。只有独立派发功能，或需求原文明示更新派发状态、保存派发结果或写入其他持久化数据组时，才额外计派发业务 W。

**功能过程：派发/审批 XX 工单**

1. E：接收 XX 工单派发/审批请求
2. R：查询流程下一环节、处理人或当前流程数据
3. W：写入工单派发/审批结果
4. X：返回处理结果

### 10.9 定时文件采集 — 拆为两个功能过程

若“采集文件”和“汇总入库”是两个可识别的独立处理阶段，可拆为：

**A. 定时采集 XX 文件：EW**

1. E：定时触发 XX 文件采集任务
2. W：下载并保存 XX 文件到本系统

**B. 定时汇总 XX 文件数据：ERW**

1. E：定时触发 XX 文件汇总任务
2. R：读取已保存的 XX 文件
3. W：写入 XX 业务数据表

是否拆成两个功能过程必须根据真实调度、触发和业务边界判断。

### 10.10 定时文件采集 — 单功能过程

若一个定时任务从对端下载文件后直接完成持久化和业务入库，可参考：

1. E：定时触发 XX 文件采集任务
2. W：下载并保存 XX 文件
3. W：写入 XX 业务数据

最终以真实数据流为准，不得仅因模板存在就重复计量。

### 10.11 短信发送类：ERWX

**功能过程：发送 XX 短信**

1. E：触发 XX 短信发送任务
2. R：获取短信业务数据、收件人等
3. W：保存确有业务价值且需求要求持久化的短信发送信息（可选）
4. X：发送 XX 短信给用户

若系统不持久化短信结果，不得强行增加 W。

### 10.12 外部系统查询接口：ERX

**功能过程：查询/同步 XX 数据（本系统作为被调用方）**

1. E：接收外部系统 XX 接口请求
2. R：查询并封装 XX 业务数据
3. X：返回 XX 接口响应结果

### 10.13 外部系统写入/同步接口：EWX

**功能过程：同步 XX 数据（本系统作为被调用方）**

1. E：接收外部系统 XX 数据同步请求
2. W：写入 XX 业务数据
3. X：返回 XX 接口处理结果

若同步前需读取已有数据，可根据真实业务增加 R；不再设置 2～4 行硬上限。

### 10.14 本系统主动调用外部系统：允许 X→E

当用户在本系统发起业务处理，本系统再调用一个或多个外部系统时，可参考：

1. E：接收用户业务请求；
2. X：向外部系统发送查询/处理请求；
3. E：接收外部系统返回结果；
4. W：保存业务结果（若真实落库）；
5. X：向用户返回最终结果。

若连续调用多个外部系统，可出现多组 `X → E`，例如：

`E → X(A系统) → E(A响应) → X(B系统) → E(B响应) → X(用户)`

这类功能过程可以超过 4 条。禁止为了满足旧版“一 E/最多四行”规则而错误拆分或删除真实外部响应 E。

### 10.15 定时统计类：ERW

**功能过程：定时统计 XX 数据**

1. E：定时触发 XX 数据统计任务
2. R：读取参与统计的 XX 数据
3. W：写入 XX 统计结果

如果统计结果仅实时返回用户、不持久化，应根据真实情况改为 ERX。

> 新疆专项复用度：若该定时统计功能成立，第 1 条“定时触发 E”默认按复用 0.33；R/W 仍按各自实际新增/复用情况判断。

### 10.16 新疆专项：SFTP 文件接入及共享

#### A. 定时采集外部 SFTP 文件

常见结构：

1. E：时钟/调度触发文件采集任务 —— **新疆默认复用 0.33**
2. R：读取 SFTP 认证信息 —— 仅当认证信息从持久化配置读取
3. W：保存目标文件到本系统本地/文件存储

注意：

- “认证信息”可包括主机地址、端口、用户名、密码/密钥路径；
- 若认证信息由部署环境直接注入、需求未体现读取，不要补 R；
- 若外部文件进入本系统还需要单独体现跨边界数据输入，应结合项目的软件边界确认，不能为了套模板重复计 E/W。

#### B. 生成并推送业务文件

同一“生成+推送”用户目标下，可按真实数据组出现：

1. E：新增文件事件/任务事件触发 —— **新疆默认复用 0.33**
2. R：读取生成业务文件所需的业务数据
3. W：按指定格式生成并持久化业务文件
4. W：生成并持久化独立校验文件（如文件名、记录条数）
5. R：读取待推送业务文件
6. R：读取待推送校验文件
7. R：读取 SFTP 认证信息（条件项）
8. W 或 X：向目标 SFTP 写入/发送业务文件
9. W 或 X：向目标 SFTP 写入/发送校验文件
10. X：返回推送/导出结果（仅有真实功能用户接收结果时）

其中第 8、9 项必须先确认目标 SFTP 是否处于被度量系统持久存储边界内。

**格式拆分经验：** 新疆经验表提出“一种格式一个过程/每增加一种输出格式可增加一个 Write”的猜测性建议。该条不得自动执行；只有 CSV、Excel 等格式确实形成独立业务需求、独立持久化文件或独立用户选择结果时，才允许分别计量。

> 经验表另有“CSV 直接输出给用户下载，算 E”的猜测性文字，与本规则 E/X 边界定义不一致。本版不将其固化为硬规则；直接输出给用户仍按真实流向优先判 X，若设计院后续确认新疆有特殊口径再单独更新。

### 10.17 新疆专项：数据库中数据汇总

常见结构：

1. E：定时/时钟触发汇总任务 —— **新疆默认复用 0.33**
2. R：从源表 A 读取原始数据
3. R：从源表 B 读取原始数据
4. ...：每个真实独立源表/数据组分别 1 个 R
5. W：将汇总结果写入目标结果表
6. X：向功能用户/外部系统输出任务结果（可选）

规则：

- “汇总、计算”本身不是数据移动，不另计；
- 多个 R 必须把数据组和数据属性写清楚，不能都笼统写成“终端 SN 列表”“业务数据”，否则容易被审核判同类复用；
- 仅记录任务执行日志不等于 X；写日志表应按日志规则判断 W；
- 若没有任何功能用户/外部系统接收汇总结果，第 6 项不计。

### 10.18 新疆专项：Kafka 接入及共享

#### A. 数据接收与存储（Kafka 位于被度量边界内）

1. E：接收上游外部系统的数据消息
2. W：写入 Topic A
3. W：写入 Topic B
4. ...：需求明确多个不同 Topic 时，每个独立 Topic 1 个 W
5. X：向上游返回 ACK（成功/Offset 或失败原因）

#### B. 数据消费与返回

1. E：接收下游消费请求（Topic、Group ID、Offset/时间戳、拉取数量等）
2. R：从 Topic A 读取消息
3. R：从 Topic B 读取消息（如需求明确）
4. X：返回消息给下游系统

注意：

- Topic 才是可比较的逻辑数据组；分区、副本、Offset 不是可继续拆分的功能过程；
- 若 Kafka 是外部中间件而非被度量软件的一部分，生产消息应按 X、消费进入应按 E 重新判断，不能照抄上述 W/R。

### 10.19 新疆专项：实时交互接口

#### A. 本系统作为服务端

常见结构：

1. E：接收外部系统请求
2. R：读取接口配置/业务映射（可选）
3. R：读取校验/参考数据（可选）
4. W：写入目标表 A
5. W：写入目标表 B
6. W：写接口调用日志（条件项）
7. X：返回同步响应
8. X：发送异步通知（可选；不同独立通知方式可分别计 X）

要求：

- 配置/映射 R 只有在需求明确“从配置表/配置文件读取”时存在；硬编码字段转换不计 R；
- 校验 R 必须是实际读取独立持久化参考数据，不能把“校验”动作本身当 R；
- 多个目标表分别计 W，但多个字段更新不能拆多个 W；
- 异步 MQ、回调等若是不同独立边界输出，可分别计 X。

#### B. 本系统作为客户端主动调用外部系统

常见结构：

1. E：用户/外部事件/有效定时任务触发；若仅技术定时器无独立业务需求则不计
2. R：读取服务端配置（条件项）
3. R：读取源表 A
4. R：读取源表 B
5. R：读取源表 C
6. R：读取字段映射配置（仅配置化映射）
7. X：向外部系统发送请求
8. E：接收外部系统响应
9. W：更新目标表 1
10. W：更新目标表 2
11. W：写接口调用日志（条件项）

若第 1 项属于新疆认可的有效定时任务初始触发，复用度默认按 0.33；其他 R/W/X 不因此自动复用。

## 11. 大模型拆分执行流程

模型必须按以下顺序工作，不得跳过直接生成结果。

### 步骤 0：加载历史评审判例库并建立查重索引

若提供了已评审拆分表，先建立以下索引：

- 功能过程名称/业务目标；
- 子过程语义；
- E/R/W/X；
- 数据组；
- 数据属性；
- 功能逻辑；
- 评审备注；
- 最终复用度/CFP；
- 被引用行号。

后续每生成一个候选功能或子过程，都应先与历史索引比对，但必须区分：

- **同一项目现状/同一既有能力**：可直接用于 1 / 0.33 / 0 判定；
- **其他需求单/其他项目的类似评审案例**：只用于学习判定逻辑、核减原因和风险模式，不得自动继承复用度。

### 步骤 1：识别需求边界

提取：

- 功能用户；
- 外部系统；
- 定时调度器；
- 核心业务对象；
- 用户可识别的业务目标；
- 触发事件；
- 数据存储对象；
- 输入/输出接口或文件。

### 步骤 2：排除非 COSMIC 内容

先标记并排除：

- 设计、开发、测试、部署、环境/运维配置、迁移；
- UI/UE；
- 技术调优；
- 纯前端动作；
- 单纯算法、计算、校验、解析；
- 纯技术/运维日志（业务审计日志另行判断）；
- 无独立数据移动的技术实现内容。

### 步骤 3：形成候选功能过程

每个候选功能过程必须回答三个问题：

1. 谁触发？
2. 为什么触发？
3. 完成后用户得到什么业务结果或系统产生什么持久化结果？

无法回答的，不直接计量。

### 步骤 4：逐项识别 E/R/W/X

按照真实数据流向判断：

- 边界外 → 程序：E
- 持久存储 → 程序：R
- 程序 → 持久存储：W
- 程序 → 边界外：X

### 步骤 5：检查功能过程结构

必须满足：

- 第一个是触发型 E；
- 至少 2 个真实数据移动；
- 至少包含 W 或 X；
- 最后一条通常为 W 或 X；
- 后续 E 只能是有依据的外部响应进入；
- 不允许无业务依据的连续 E；
- 不设置最多 4 条硬限制，但超过 4 条时逐条证明其必要性；
- 若多条只是模板补 R/W/X，应删除；
- 若多个独立用户目标被拼在一起，应拆分功能过程。

### 步骤 6：填写数据组和数据属性

数据组、数据属性必须：

- 与子过程动作一致；
- 来自需求或可明确推导的业务对象；
- 不为空；
- 不人为制造差异。

### 步骤 7：执行三轮重复/复用扫描

**第一轮：历史评审库级**

检查当前候选是否已被历史评审表标为：

- 数字行引用；
- 复用；
- OLD；
- O；
- 功能重复/包含/合并；
- 上传/下载/日志等通用能力。

有明确判例时优先沿用**判定逻辑**；只有确认属于同一现状能力时，才沿用其具体复用/利旧结论。

**第二轮：当前输出功能过程级**

检查是否存在名称不同但业务目标、功能逻辑、数据对象实际上相同的功能过程。

**第三轮：子过程级**

比较：

- 子过程语义；
- 数据移动类型；
- 数据组；
- 数据属性；
- 功能逻辑。

注意使用**语义相似**而不是字符串完全一致。改名、换字段顺序、同义词替换不能规避复用。

### 步骤 8：执行审核清零/降复用检查

重点扫描：

- 首行不是 E；
- 只有一个真实数据移动；
- 只有 E；
- 无依据的额外 E/R/W/X；
- N / NM / OLD / UIUE / C / NR / 算法本体 / 需求文档不涉及；
- 纯前端；
- 查询/展示重复；
- 字段级拆分；
- 功能被其它完整功能包含；
- 模板化批量拼接；
- 无真实数据移动依据、数据组或边界方向错误的子过程；固定使用“读取相关数据/保存处理结果/返回处理结果”等表述本身不构成新疆项目风险；
- 四项关键字段为空；
- 与**同一现状能力**的历史行语义重复却仍计 1；
- 通用上传/下载/日志/短信等未先查复用；
- CFP 不是 1 / 0.33 / 0；
- 非 COSMIC 内容被计入；
- 新疆有效定时任务初始触发 E 被误判为新增 1，而未执行 0.33 专项规则；
- 新疆 SFTP/Kafka 场景未确认软件边界就机械使用 W/R；
- 多源表、多目标表、多 Topic 被合并在一个 R/W 中，或反过来按分区/字段过度拆分；
- 配置读取、映射读取、校验参考数据、接口日志、异步通知等“可选项”在需求未体现时被自动补出；
- “猜测”经验被直接写入 CFP，而未进入人工审核/待确认。

## 12. 输出前强制自检清单

模型输出最终拆分结果前，逐个功能过程执行以下检查。

### 12.1 结构检查

- [ ] 功能过程名称是“动作 + 业务对象”
- [ ] 触发事件与功能过程一致
- [ ] 第一条数据移动为触发型 E
- [ ] 只有一个初始触发 E
- [ ] 后续 E 均可解释为外部系统响应进入
- [ ] 新疆定时/系统事件触发已先判断“功能是否成立”，成立后初始 E 未误判为新增 1
- [ ] 没有无依据的连续 E
- [ ] 至少有 2 个真实数据移动
- [ ] 超过 4 条时每条都有业务/边界依据
- [ ] 最后一条通常为 W 或 X
- [ ] 功能过程中存在真实数据移动

### 12.2 内容检查

- [ ] 子过程描述与功能过程动作一致
- [ ] 每个 R 确实读取了持久化数据
- [ ] 每个 W 确实写入了持久化数据
- [ ] 一个 R / W 只对应一个逻辑持久化数据组；同一过程更新多个对象时已分别列出多个 R / W
- [ ] 多源表、多目标表、多 Topic 已按真实独立数据组拆分，且没有按分区/字段过度拆分
- [ ] SFTP/Kafka/外部接口已明确被度量软件边界后再判 R/W/E/X
- [ ] 每个 X 确实跨系统/用户边界输出
- [ ] 校验/计算/解析没有被单独冒充数据移动
- [ ] 没有把纯技术日志当功能计量；业务审计日志已优先检查复用
- [ ] 接口配置/映射 R、校验参考数据 R、接口日志 W、异步通知 X 等可选项均有需求原文依据
- [ ] 没有纯前端计量
- [ ] 没有开发实现术语替代业务描述

### 12.3 粒度检查

- [ ] 没有按字段拆分功能过程
- [ ] 没有把同一查询拆成“查询 + 展示”两个功能过程
- [ ] 没有将同数据组、同接口、同逻辑重复拆分
- [ ] 没有为增加功能点而过度拆分

### 12.4 数据检查

- [ ] 子过程描述不为空
- [ ] 数据移动类型不为空
- [ ] 数据组不为空
- [ ] 数据属性不为空
- [ ] 数据组和数据属性与功能过程相关
- [ ] 数据属性没有人为虚构或无依据扩充

### 12.5 设计院评审标签检查

- [ ] N：已删除不存在/非必要步骤
- [ ] NM：已删除无数据移动动作
- [ ] 数字行号：已读取对应历史行并判断复用/重复
- [ ] O/OLD：已按既有能力处理
- [ ] UIUE/C：已排除非功能需求
- [ ] NR：已重新按 COSMIC 规则处理
- [ ] 算法：只保留算法输入输出/持久化数据移动
- [ ] 需求文档不涉及：已删除，无自行补写
- [ ] “包含在某功能/合并为某功能”没有重复计量

### 12.6 复用检查

- [ ] 已对全部功能过程进行全局重复扫描
- [ ] 相似度高的子过程已标记复用候选
- [ ] 三要素全同未错误计 1
- [ ] 三要素两项相同未错误计 1
- [ ] 跨层/跨边界判 1 时有明确依据
- [ ] CFP 仅使用 1 / 0.33 / 0
- [ ] 历史案例来自其他需求单时只继承判定逻辑，没有直接继承其“复用某部分”等具体结论
- [ ] 新疆经验表中的“猜测”项没有自动影响 CFP

## 13. 模型禁止行为

模型绝对不得：

1. 为提高造价主动虚构需求；
2. 为降低复用率人为改数据属性；
3. 将一个字段拆成一个功能过程；
4. 将一个技术步骤拆成一个功能点；
5. 把纯计算、校验、解析、过滤当作独立数据移动；
6. 把无需求依据的技术日志/框架日志作为 W 计量，或把通用业务日志直接判新增；
7. 机械为所有功能生成 ERWX；
8. 看到“查询”就固定 ERX、看到“新增”就固定 EWX，而忽略真实需求；
9. 仅修改描述文字来规避重复；
10. 在需求未说明持久化时虚构数据库写入；
11. 在需求未说明读取时虚构 R；
12. 在需求未说明外部输出时虚构 X；
13. 对不确定内容自行猜测并直接计入 CFP；
14. 为满足固定“2～4 行”模板删除真实外部系统 X→E 交互；
15. 通过更换功能名、字段顺序、同义词来逃避历史查重；
16. 在未检索历史评审库前，把上传、下载、日志、短信、通用查询等直接判为新增；
17. 将其他需求单中“复用某部分/复用集客”等具体结论无条件套到当前独立需求；
18. 在新疆项目中把有效定时任务初始 E 直接判为新增 1，或反过来把整个定时功能所有 R/W/X 都机械判复用；
19. 未确认 SFTP/Kafka 是否位于被度量边界内，就固定把上传/写 Topic 判 W、读取 Topic 判 R；
20. 将“可选/视需求而定/猜测”的新疆经验项当作必选模板自动补齐。

## 14. 建议的大模型最终输出格式

### 14.1 计量明细

```text
| 功能用户 | 触发事件 | 功能过程 | 子过程描述 | 数据移动类型 | 数据组 | 数据属性 | 复用度 | CFP | 备注 |
```

要求：

- 同一功能过程的多条子过程连续输出；
- 功能过程内按真实执行顺序排列，允许有依据的 X → E 外部系统往返；
- 不得缺失关键字段；
- 相同功能过程不要通过改名重复输出；
- 若判复用/利旧且存在历史参考行，在备注中写明“复用参考：第 XX 行/功能 XX”；
- 若判 0，备注应明确 N/NM/OLD/UIUE/C/NR/包含/重复/需求文档不涉及等原因。

### 14.2 待确认事项

对无法从需求中确认、但会影响 COSMIC 判定的问题单独列出，例如：

- 查询结果是否持久化？
- 导出文件是否保存到服务器？
- 接口是新增开发还是复用已有接口？
- 定时采集和数据入库是否为两个独立调度任务？
- 自动填充是否调用后台接口？
- 统计结果是否落库？
- SFTP 目标目录/Kafka 集群是否属于被度量软件边界？
- 定时触发是否属于独立功能用户需求，还是纯技术调度？
- 字段映射是配置表驱动还是硬编码？
- 接口调用日志是否为明确业务/审计需求？
- 多个 Topic/源表/目标表是否确为独立逻辑数据组？

在得到确认前，不通过臆测补出额外 R/W/X。

### 14.3 风险提示

如发现以下情况，应在结果后输出风险提示：

- 需求描述过于抽象，无法确定数据移动；
- 存在大量配置/部署/迁移内容；
- 同类功能高度重复；
- 需求按页面而非业务功能描述；
- 数据属性缺失；
- 需求与历史拆分规则存在明显冲突。

### 14.4 规则门禁与人工审核

- **确定性错误（ERROR）**：包括必填项缺失、非法 E/R/W/X、复用度与 CFP 映射错误、末行不符合确定性结构约束等；必须红色提示并写入导出文件供人工修改，但不阻断审核结果保存和人工确认后的送审材料导出。
- **结构风险（RISK）**：表示需要结合原始需求和业务边界进行人工判断的候选问题；它可以在深度审核建议采纳过程中逐步减少，不要求每次采纳一条建议后整表风险立即清零。
- 确定性错误和结构风险均不阻断送审材料导出。导出功能点拆分表时，相关行和风险原因必须着色，供人工审核和最终处置。
- 一条深度审核建议只有在引入确定性错误、目标行失效或与已采纳建议冲突时才不得采纳；不得仅因表内仍存在其它结构风险而拒绝采纳。

## 15. 最终判定口诀

> **先看当前需求，再用历史校验；历史案例学规则，不跨需求继承复用；先找触发，再定过程；先看边界，再判 E/R/W/X；新疆有效定时触发 E 默认 0.33，纯技术定时器不计；多表多 Topic 按真实数据组拆，分区字段不拆；配置/日志/异步通知看原文；只写真数据移动，不补万能 R/W；功能重复判 0、子过程复用判 0.33、确有新增才判 1。**

## 16. v2.1 关键修订记录

### 16.1 延续 v2.0 的设计院评审规则

1. 取消“一个功能过程只能有一个 E”硬限制，允许真实外部系统响应形成后续 E；
2. 取消“每个功能过程最多 4 行”硬限制，改为真实性校验；
3. 将设计院评审批注 N/NM/数字/O/OLD/UIUE/C/NR/算法/需求文档不涉及纳入正式判定；
4. 新增“功能级重复=0、子过程级复用=0.33”的分层判定；
5. 强化模板化虚构 R/W、纯页面动作、字段级拆分等核减规则；
6. 日志区分技术日志与真实业务/审计日志；
7. 明确字段换序、同义词、泛化属性不能规避语义查重。

### 16.2 v2.1 新增的新疆四类特殊场景规则

1. 增加新疆经验“确定/可选/猜测”三级证据体系；
2. 修正历史判例使用边界：**不同需求单只继承判定逻辑，不直接继承具体复用结论**；
3. 新疆有效定时/系统事件初始触发 E 默认按 **复用 0.33**，纯技术定时器先判是否不计；
4. 新增 SFTP 文件定时采集、文件生成/校验/推送专项模板；
5. 新增数据库定时汇总专项模板：多个独立源表分别 R、目标结果表 W；
6. 新增 Kafka 接入/共享专项模板：多个独立 Topic 可分别 W/R，但禁止按分区/副本拆分；
7. 新增实时交互接口服务端/客户端专项模板；
8. 明确接口配置、业务映射、校验参考数据只有在真实持久化读取时才计 R，硬编码不计；
9. 明确多目标表写入可分别计 W，多源表读取可分别计 R；
10. 接口调用日志仅在需求明确要求持久化业务/审计记录时计 W；
11. 多种异步通知方式仅在真实形成不同边界输出时分别计 X；
12. SFTP/Kafka 场景新增“先确认被度量软件边界，再判 W/R/X/E”的强制门禁；
13. 对“一种格式一个过程”“每种格式增加 Write”等猜测性经验只作为人工审核提示，不自动增加 CFP；
14. 对经验表中“CSV 直接输出给用户算 E”等与通用边界定义冲突的猜测项不固化，继续按真实数据流向判定。
